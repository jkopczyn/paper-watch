# Public site: digest history and ratings at papers.cupchinski.com

**Date:** 2026-11-08
**Status:** approved direction (conversation 2026-11-08), pre-plan

## Purpose

Publish the list of papers paper-watch has suggested, with the reading group's
aggregate ratings where they exist, as a static site at
`https://papers.cupchinski.com`. The site is regenerated and pushed by the same
systemd tick that sends digests, so it stays current without manual steps.

Decisions already fixed by the user:

- Only papers that appeared in a digest (the `shown` table) are listed.
- The landing page is one section per digest, matching the email layout. A
  single filterable table and a JSON file exist but are reached by link only.
- Published on every digest send and every Thursday feedback refresh.
- Hosted from a new repo on GitHub Pages at the subdomain
  `papers.cupchinski.com`, not inside the existing `jkopczyn.github.io` repo.
- DNS is on Cloudflare; the CNAME record is added with the `cf` CLI.
- Nothing about individual voters is published. The store holds only per-paper
  aggregates (`feedback.group_rating`, `feedback.picked`, `readings`), so no
  new exclusion is needed.
- The internal `score` is not published. Rank within a digest is.

## Hosting

- New public GitHub repo `jkopczyn/paper-watch-site`, default branch `main`,
  GitHub Pages serving from the root of `main`.
- `CNAME` file containing `papers.cupchinski.com`.
- Cloudflare DNS: `CNAME papers -> jkopczyn.github.io`, DNS-only (grey cloud)
  so GitHub can issue its certificate. Enforce HTTPS in Pages settings once the
  certificate exists.
- The repo holds generated files only (`index.html`, `all.html`,
  `papers.json`, `CNAME`) plus one hand-written `style.css` and a short
  `README.md` saying the content is generated by paper-watch and should not be
  edited by hand. The stylesheet is authored in paper-watch and copied on each
  publish, so the site repo never needs a hand edit.

## Data

One record per `shown` row, joined to its entry:

| field | source |
|---|---|
| `digest_at` | `shown.digest_at` |
| `rank` | `shown.rank` |
| `resurfaced` | `shown.resurfaced` |
| `title` | `entries.title` |
| `authors` | `entries.authors_json` |
| `url` | the same link the email shows first (reuse `_display_links` / `_prefer_alignmentforum` from `runtime.py`) |
| `arxiv_id` | `entries.arxiv_id`, may be null |
| `published` | `entries.published_at`, else the same estimate the email shows, with an `is_estimate` flag (reuse `_pub_display`) |
| `tags` | `entries.tags_json` |
| `tldr` | `entries.tldr`, may be null |
| `group_rating` | `feedback.group_rating` for any week, latest week wins; null if none |
| `picked` | true if any `feedback.picked` row for the entry |
| `read` | true if any `readings` row points at the entry |

Not published: `score`, `why`, `abstract`, source labels, Slack channel names,
anything from `mentions`, the `explanation` string.

A paper shown in more than one digest appears under each digest it was in,
marked resurfaced where `shown.resurfaced` is set. In the single table it
appears once, under its first digest, with a count of later appearances.

## Pages

`index.html`: header with the site name and a one-sentence description. Then
one section per distinct `digest_at`, newest first, headed by the digest date.
Within a section, entries in rank order, each showing title (linked), authors,
published date (with `~` when estimated), tag chips, and a rating marker when
present: `rated N` for `group_rating`, `read` for `read`, `picked` for `picked`
without a rating. The `tldr` is in a collapsed `<details>` under each entry.
Footer links to `all.html` and `papers.json`.

`all.html`: one table, newest first digest at the top. Columns: title (linked),
authors, published, tags, first digest date, rank, times shown, rating marker.
A text box filters rows by title and author substring, and clicking a tag chip
filters to that tag; both are a few dozen lines of inline JavaScript with no
framework and no network requests. Works as a plain table when JavaScript is
off.

`papers.json`: `{"generated_at": iso, "digests": [{"digest_at": iso, "entries":
[record, ...]}, ...]}` using the fields above.

Rendering reuses the Jinja setup in `digest.py` (autoescape on). Templates live
in a new `src/paper_watch/site.py` as module-level strings, matching how the
email template is kept, or as files under `src/paper_watch/templates/` if the
implementer finds the strings too long; either is acceptable.

## Publish command and tick wiring

New config block:

```yaml
site:
  repo_path: ../paper-watch-site     # local checkout of the site repo
  remote: origin
  branch: main
```

Absent block means the feature is off and nothing in the tick changes.

New `paper-watch publish [--config] [--dry-run]`:

1. Render the three files plus `style.css` and `CNAME` into `repo_path`.
2. If `git status --porcelain` is empty, log "site unchanged" and exit 0.
3. `git add -A`, commit with message `site: <N> digests, <M> papers (<ISO
   timestamp>)`, push `branch` to `remote`.
4. `--dry-run` renders and reports the diff summary but does not commit or
   push.

Preconditions checked before step 1, each a clear error: `repo_path` exists
and is a git checkout; the working tree is clean apart from generated files;
the current branch is `branch`.

Tick wiring in `runtime.py`: after a successful send (where `record_shown` is
called) and after a successful `run_feedback_refresh`, call the publish
function. The call is wrapped so that any exception is logged as a warning and
recorded with `store.record_source_failure("site", label="site publish", ...)`;
success calls `record_source_ok("site", ...)`. This puts a failing publish into
the existing source-warning block at the top of the next digest and into the
same health machinery as a dead feed. The send watermark and `record_shown`
are never affected by publish failure. Dry-run ticks do not publish.

## Credentials

A GitHub deploy key with write access scoped to `paper-watch-site`. The private
key file path goes in `.env` as `SITE_DEPLOY_KEY`. The push runs with
`GIT_SSH_COMMAND="ssh -i $SITE_DEPLOY_KEY -o IdentitiesOnly=yes"` so the
headless timer never needs the desktop keyring. If `SITE_DEPLOY_KEY` is unset,
publish uses the ambient git configuration (fine for manual runs). The README
gets a failure note next to the SMTP one: a revoked or missing key shows up as
a `site publish` warning in the digest.

## Setup steps outside the codebase

Done in this feature, recorded in the report:

1. Create the `paper-watch-site` repo with `gh repo create --public`.
2. Generate the deploy key, add it to the repo with `gh repo deploy-key add
   --allow-write`, store the private key next to `.env`.
3. Clone the site repo to the configured `repo_path`.
4. Run `paper-watch publish` once by hand to seed the repo, then enable Pages
   from `main` root with `gh api`.
5. Add the Cloudflare CNAME with the `cf` CLI, then set the custom domain and
   enforce HTTPS in Pages settings.

## Testing

- `test_site.py`: record query against a fixture store with entries, several
  `shown` rows including one resurfaced paper, a `feedback` row, and a
  `readings` row. Assert field mapping, latest-week rating, resurfaced
  handling, and that excluded fields are absent from the JSON.
- Renderer tests: each page renders, contains every title, escapes a title
  with `<` in it, and `index.html` orders digests newest first with entries in
  rank order.
- Publish tests against a temporary bare repo as `origin`: first publish
  commits and pushes; a second publish with unchanged data makes no commit;
  a push failure (remote path removed) raises and leaves the local commit;
  `--dry-run` leaves the repo untouched. The tick wrapper test asserts that a
  raising publish records a `site` failure and does not raise out of
  `run_pipeline`.
- No network in tests.

## Out of scope

RSS or Atom for the site, per-paper pages, intake of suggestions from group
members, analytics, and any change to how ratings are imported.
